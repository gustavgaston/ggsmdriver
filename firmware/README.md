# GGSMDriver firmware

Firmware for the GGSMDriver board (STM32G0B1CBT6 + TMC2209): the **ggstepper**
stepper library (core only) and the **Automato serial bridge**
(`automato.serial.v2`), ported from Arduino/AVR to ST's HAL. The module is meant
to drop in where the Uno + ggstepper was used.

**Status: compiles and links. Nothing has been run on hardware.** No claim is
made about timing, motion, USB enumeration or the TMC2209 UART beyond that.

There is no `.ioc`: the project is not generated by STM32CubeMX; it is plain
sources, a Makefile and hand-adapted CubeIDE project files.

## Layout

| Folder | Content |
|---|---|
| `Core/Src`, `Core/Inc` | `main.c`, interrupt handlers, HAL MSP, `board_time` (micros/delay), `serial` (USB serial shim), `board_pins.h`, `ggstepper_conf.h`, HAL config |
| `Core/Startup` | ST's `startup_stm32g0b1xx.s` (vector table, reset handler) |
| `ggstepper/` | `ggstepper.c/.h` (ported library), `ggstepper_automato.h` (adapter), `ggstepper_hw.c/.h` (new STM32 hardware layer) |
| `automato_bridge/` | `automato_bridge.c/.h` (ported bridge) |
| `USB_Device/App`, `USB_Device/Target` | CDC glue and descriptors, derived from ST's `CDC_Standalone` example (STM32G0C1E-EV, same USB IP) |
| `Drivers/`, `Middlewares/` | Vendored ST HAL, CMSIS, USB Device library (only the needed files, licenses kept) |
| `STM32G0B1CBTX_FLASH.ld` | Linker script: 128 KB flash at `0x08000000`, 144 KB RAM |

ST sources are from github.com/STMicroelectronics: `STM32CubeG0` `51075a5`
(CMSIS core headers, example and template projects), `stm32g0xx_hal_driver`
`289ef6c`, `cmsis_device_g0` `7c77b7c`, `stm32-mw-usb-device` `2df324b`.

## Build

### Command line

```sh
make            # build/ggsmdriver.elf, .bin, .hex, then arm-none-eabi-size
make clean
make OPT=-Og    # other optimization level (default -Os)
```

Needs `arm-none-eabi-gcc` (built with 13.2.1). Our own files build with
`-Wall -Wextra` and no warnings; ST's files build with `-w`.
Debug DIAG reports: `make EXTRA_CFLAGS=-DGGSTEPPER_DEBUG=1` (see below).

Last build (`-Os`): text 60912, data 732, bss 12252 bytes, so about 61.6 KB of
the 128 KB flash and 13 KB of the 144 KB RAM (plus the 4 KB stack minimum the
linker script reserves).

### STM32CubeIDE

*File > Import > General > Existing Projects into Workspace*, select this
`firmware` folder. The `.project` / `.cproject` are adapted from ST's
`NUCLEO-G0B1RE/Templates` CubeIDE project (MCU `STM32G0B1CBTx`, defines
`STM32G0B1xx USE_HAL_DRIVER`, include paths, linker script
`STM32G0B1CBTX_FLASH.ld`). Use the **Release** configuration (`-Os`) for
anything that moves the motor: the Debug configuration is `-O0`, and the STEP
interrupt does its planner math inside the pulse deadline. The CubeIDE files
could not be opened here; see "Unverified" below.

## Flash over USB DFU

No custom bootloader: the ROM DFU bootloader is used, app at `0x08000000`.

1. Hold **BOOT**, tap **RESET**, release BOOT. The board appears as a DFU device.
2. Either STM32CubeProgrammer (USB connection, open `build/ggsmdriver.hex` or
   `.bin` at `0x08000000`), or
   `dfu-util -a 0 -s 0x08000000:leave -D build/ggsmdriver.bin`.

If the ROM bootloader is not entered, check the `nBOOT_SEL`/`nBOOT0` option bytes
(the BOOT button drives PA14-BOOT0); not checked here.

SWD on J6 (STDC14, STLINK-V3MINIE cable) works with CubeIDE's debugger. USART1
(PB6 TX, PB7 RX) is wired to the STLINK virtual COM port (J6 pins 14/13) but not set up in firmware yet.

## What is ported

Scope confirmed by the owner (requirements.md, "Confirmed 2026-10-17"):
ggstepper core only.

- TMC2209 UART setup (same registers and values as before)
- StallGuard/DIAG homing, normalized moves (`ggstepper_move_normalized`), motion
  profile, brake/stop, status
- The `GGSTEPPER_DEBUG` DIAG reports (default off, like the Nodharmonica sketch)
- The Automato adapter (`GGSTEPPER_AUTOMATO_POSITION`, `GGSTEPPER_AUTOMATO_SPEED`)
- The Automato bridge, and a `main.c` that does what the ggstepper part of
  `nodharmonica_automato.ino` does: init, home, register the position and speed
  controls, run the bridge, poll. No fan.

Not ported: sequences (`GGSTEPPER_SEQUENCE_CAPACITY` stays 0) and calibration
(`GGSTEPPER_CALIBRATION` 0). Their code was removed from `ggstepper.c`/`.h`
rather than left half-ported; `ggstepper.h` fails to compile if either macro is
set. The ggstepper logic and public API are otherwise unchanged. The Automato
bridge's own sequencer (`SEQ ...` commands, `AUTOMATO_SEQUENCE_CAPACITY`) is
unchanged and works as before.

`ggstepper.c` is now its own translation unit (the `.c` is no longer included from
the header); `ggstepper_conf.h` is included by `ggstepper.h`.
`ggstepper_automato.h` still holds function definitions, so include it from one
file only (`main.c`).

## What changed from the AVR version

### STEP timing (Timer1 -> TIM3)

TIM3 counts 1 MHz ticks (prescaler 63 at 64 MHz). It replaces Timer1's CTC
mode: the counter runs to a top value `ticks - 1`, an update interrupt fires at
the wrap, and the new top takes effect immediately (no auto-reload buffering),
exactly like `OCR1A`. The interrupt body is the former `TIMER1_COMPA_vect`: it
sets the top to 65535, emits the high pulse (`GGSTEPPER_STEP_HIGH_US`), lowers
STEP, then plans the next interval. Long intervals span several 60000-tick
cycles. A new interval that does not end more than `GGSTEPPER_DEADLINE_MARGIN_TICKS`
after the current count stops the move and invalidates the position (the old
`top <= TCNT1 + 8` check). STEP (PA6) is driven as a plain GPIO from the
interrupt; it is also TIM3_CH1 but PWM/one-pulse hardware is not used.

Representability limits come from this timer, not from `F_CPU / 8`: the
shortest accepted period is `STEP_HIGH_TICKS + DEADLINE_MARGIN_TICKS + 2` ticks.
That is only what the timer can express; the real limit is the unmeasured
interrupt time (see TODO list).

### micros() and delays

`micros()` comes from TIM17: a 16-bit counter at 1 MHz extended to 32 bits by
its update interrupt (wraps every 71.6 min like Arduino's). TIM2, the only
32-bit timer, is reserved for the encoder on PA0/PA1; Cortex-M0+ has no DWT
cycle counter; SysTick stays the HAL tick. `micros()` is safe from any
context. `delay_us()` busy-waits on TIM17's counter for at least N and at most
N+1 microseconds (the STEP pulse); `delay_ms()` uses `micros()`.

### Interrupt priorities

0: TIM3 (STEP) and EXTI1 (DIAG); 1: SysTick and TIM17; 2: USB. SysTick must
preempt USB because the USB library calls `HAL_Delay` from the USB interrupt.

### DIAG (pin-change ISR -> EXTI1)

PB1, both edges. `ggstepper_diag_isr()` is the old ISR body (reads the level,
latches the endpoint, drops STEP).

### TMC2209 UART (bit-banged -> USART2, echo handling)

USART2 at `GGSTEPPER_UART_BAUD` (19200, unchanged from the AVR configuration).
PA2 TX goes through 1 k to PDN_UART and PA3 RX is wired to the same line, so
every transmitted byte comes back on RX. `ggstepper_hw_uart_send()` therefore
sends one byte at a time and reads each byte's echo (and compares it) before
sending the next, so the echo never reaches the reply parser. A missing or
different echo is reported by the debug register reads (`uart=...:timeout` or
`frame`); register writes do not check it (as before, the TMC2209 does not
acknowledge writes), and after a failed echo the rest of the frame is still sent
without waiting. Reads wait for 12 idle bit times on the RX pin first, send the
4-byte request, discard its echo, then read the 8-byte reply with the 20 ms
`GGSTEPPER_UART_READ_TIMEOUT_MS`. The UART is only used while STEP is stopped.
UART address 0.

### Serial: Arduino `Serial` -> USB CDC

`Core/Src/serial.c` implements the part of `Serial` that the code uses
(`serial_print` / `serial_println` for strings, integers and floats, with
`serial_print_float(x, n)` for N decimals, `serial_print_hex`,
`serial_available`, `serial_read`, `serial_flush`). Printing goes to a 2 KB ring
that `serial_poll()` (main loop) hands to the CDC endpoint in 256-byte chunks;
reception goes into a 1 KB ring and NAKs the host when full. `println` ends with
`\r\n`, as Arduino's does. Floats use Arduino's `printFloat` algorithm in
64-bit `double` (AVR's `double` was 32-bit, so the trailing digits of some
values can differ).

Behavior that differs from an Uno, on purpose:

- Output is dropped while the host has not opened the port (DTR low). An Uno
  resets when the port is opened and prints the descriptor; USB CDC does not reset,
  so the bridge repeats its descriptor (`automato_announce()`) each time the host
  opens the port, which is what the Automato host waits for at connect.
- The descriptor's `clock_resolution_us` is 1 (this board's `micros()` ticks at
  1 us) instead of the AVR's 4: `AUTOMATO_CLOCK_RESOLUTION_US` in
  `automato_bridge.h`. This is the only change to the protocol text; the keys,
  order and framing are the AVR bridge's.
- The baud rate set by the host is accepted and ignored.

USB: FS device, CDC ACM, VID/PID `0x0483:0x5740` (ST's sample ID, see TODO),
product "GGSMDriver Automato bridge". System clock 64 MHz from HSI16 through the
PLL; USB clock from HSI48 trimmed by the CRS from the USB SOF (as in ST's
example). The USB stack is ST's USB Device library with the CDC class.

`GGSTEPPER_TIMER_TICKS_PER_US` 1 and `GGSTEPPER_DEADLINE_MARGIN_TICKS` 4 in
`ggstepper_conf.h`; `AUTOMATO_DEVICE_NAME` in `main.c`; the serial buffer sizes
and timeouts at the top of `serial.h`.

### Motor current (to confirm with the owner)

IRUN = IHOLD = 3 with VSENSE = 1 are kept as they were. With the TMC2209
datasheet formula `I_RMS = (CS+1)/32 * V_FS / (R_SENSE + 0.02 ohm) / sqrt(2)`,
V_FS = 0.18 V (VSENSE = 1), R_SENSE = 0.05 ohm on this board:

- 4/32 * 0.18 / 0.07 = 0.321 A peak = **0.227 A RMS**, run and hold.

The Adafruit TMC2209 breakout schematic (R1/R2, 0.05 ohm, between BRA/BRB and
GND) has the same sense resistors, so the same values give the same current on
the old board, if the old board was that breakout. The Automato configurator
also assumes 0.05 + 0.02 ohm. So there is no change in current from the board
swap; nothing was changed. Because `GCONF` has `i_scale_analog` = 0, VREF does not
set the current; the board ties it to GND and has no trimmer.
